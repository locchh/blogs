When Code Is Cheap

A feature that used to take an afternoon now takes an agent twenty minutes. That speed does not remove the hard question. It moves it. A senior is no longer asked how to build the feature. They are asked whether the project should use AI at all, and whoever decides has to live with the answer.

Fred Brooks saw this coming in 1986. In No Silver Bullet he split software work into the essence, the ideas and rules a program must get right, and the accident, the labor of typing those ideas into a machine. Then he said which part is hard: “the specification, design, and testing of this conceptual construct, not the labor of representing it.” Agents made the labor cheap, so the essence is now the whole job. And the first piece of it is the one he called hardest: “deciding precisely what to build.”

This post breaks that job into eleven questions to ask before and after saying yes to AI in a project. Each question has a reason from the fundamentals of our field and a reason from Microsoft’s own guidance for people who make this decision, with links to go deeper. It is meant to be used, not admired. If you only have five minutes, read the table near the end. After the questions, the post applies them to five kinds of delivery work. It ends with personal notes on the work left for the people who build, and two questions I cannot answer yet.

One honesty note before the list. Two kinds of Microsoft sources appear here. The Cloud Adoption Framework, the Well-Architected Framework, and the Agents hub are official documentation. The Microsoft AI Decision Framework is a practitioner’s guide published on Microsoft’s GitHub. It says itself that Microsoft’s AI products change weekly and that production decisions should be checked against official sources. I quote it because its sentences are the sharpest, and I say which is which.

Before you say yes

The first four questions decide whether there is a project at all. They move from the problem, to whether AI is the right tool for it, to the shape the solution should take, to the decisions that will be expensive to change later.

1. What is the problem, before AI?

Microsoft’s planning guide opens with a sentence every request should come with: start with business problems, and look for where results miss expectations “before you consider AI at all.”

Most requests arrive as a solution instead. Someone asks for a chatbot because a chatbot is the solution they can picture. Users know what they want, but they rarely know what their problem is. So go and watch the work first. Maybe staff cannot find the answer. Maybe they find it in seconds and then wait a day for a manager’s approval. A chatbot fixes the first and does nothing for the second. Only the people doing the work know which one they have.

Once the problem is clear, measure the work as it is today: how long each case takes, how many are finished, how many come back. Without that number there is nothing to compare against later, and every result will look like success. The business plan guidance for agents says the same thing in one line: record today’s performance to create a baseline, before any development begins.

Lesson: describe the delay or the loss before you describe the tool. If you cannot name what gets better, you are not ready to build.

Go deeper:

  • Plan for AI adoption. Argues for a fixed order: business problems first, then use cases, then an honest look at the skills and data you actually have.

2. Does it need AI at all, and does something already exist?

A clear problem still does not mean AI is the answer. The Decision Framework has a rule worth repeating in every meeting: “never lead with a product.” Describe the result first, then the situation, then how the system should behave. The technology comes last.

It also asks a checkpoint question before any of that: does this need an agent? If the steps are fixed and the input is structured, ordinary code is cheaper and more reliable. If people just need to find a document, that is search. For numbers, the scenarios page is blunt about language models, or an LLM in its words: “if the problem has a numerically correct answer, an LLM is the wrong tool for producing it.” A model is good at reading messy input. It is not a calculator and not a database. Microsoft’s official agent business plan draws the same line from the other side: agents earn their place when the task needs multistep decisions, many tools in a flexible order, or messy input that must be interpreted.

Even when AI is justified, building your own is the last step, not the first. The framework describes a ladder, roughly: use something that exists, configure it, extend it, and build only at the top. The honest part is the rule for climbing. You must be able to explain why each rung below failed. If you cannot, you are not building because you need to. You are building because building got cheap.

3. What shape should it take, and how hard is it?

Once the answer to question 2 is yes, the next mistake is to build the most impressive shape. Anthropic’s guide to building effective agents puts the rule plainly: “we recommend finding the simplest solution possible, and only increasing complexity when needed.” It adds: “This might mean not building agentic systems at all.” Microsoft’s Architecture Center says the same in its own words: “Use the lowest level of complexity that reliably meets your requirements.”

Before choosing a shape, split the request three ways: the work the model will own, the work existing systems already own, and the work people must keep. Anthropic’s architect course for partners, Claude Platform Solution Design, starts there. The model’s share usually turns out smaller than the request suggests. Its public outline adds a second check. When an answer depends on the current state of a system, such as a ticket’s status or an order in flight, ask the system directly. Searching a copy of last week’s documents gives an answer that was true last week.

With the model’s share known, pick the shape. The same course names three, and each costs more than the last.

ShapeWhat decides the next stepGood forWhat it costs you
Augmented callNothing. One model call, with retrieval, examples, or a toolClassify, summarize, translate, extract, draftA prompt, a test set, and a check on the output
WorkflowYour code. Anthropic: “systems where LLMs and tools are orchestrated through predefined code paths”Fixed steps where some need language: triage, reports, release notesAll of the above, plus the code path and a check between steps
AgentThe model. It chooses its own steps and toolsOpen-ended work where the number of steps cannot be known in advanceAll of the above, plus iteration limits, tool permissions, tracing, and a harder test set

Inside the agent row there is one more step up. Microsoft calls a single agent with tools “often the right default for enterprise use cases.” Several agents are justified only when one agent cannot cope because of prompt size, too many tools, or separate security boundaries. If the agents talk in a shared thread, the same page suggests keeping it to three or fewer. The Decision Framework puts the whole rule in one line: “Audition the soloist before you hire the orchestra.” Try one agent with good tools before anyone talks about several.

The shape says who decides the next step. It does not say how hard the work is, and that is what sets the evidence you need before launch. The Decision Framework’s evaluation criteria sort work into four tiers, and each tier lists the evidence it needs before going live. To place a project in a tier, ask six quick questions and let the hardest answer decide. That last rule is my addition, not the page’s. It rests on a simple fact: a system is as hard as its hardest part.

  1. Steps: are they fixed, or discovered along the way?
  2. Blast radius: does it only read, write records, or do something that cannot be undone?
  3. Reach: how many systems, owners, and security boundaries does it cross?
  4. Checking: can a machine tell whether the result is right? A test suite, a matching total, or the old system’s behavior all count. If only a person can tell, the review hours in question 10 grow.
  5. Drift: how often do the inputs or the right answer change?
  6. Owners: who will run it? A team that builds in a low-code tool and a team that runs CI/CD and an on-call rotation are different owners, and the tier must match the team.

4. Which decisions will be hard to undo?

The shape chosen in question 3 can be changed later. Other decisions cannot, at least not cheaply. The real solution is rarely the framework or the hosting service. It is the data model, the boundaries between systems, who owns what, and the business rules. Tools can be swapped. Those cannot.

David Parnas said this in 1972, in the paper that gave us information hiding. Split a system around the design decisions most likely to change. Hide each one behind a stable boundary. Then changing one decision does not force everything else to change. It is still the best guide to where a senior’s attention should go. Spend it on decisions that are hard to undo. Let the agent produce the cheap, throwaway parts: screen drafts, glue code, prototypes.

A working order follows from this: design top-down and build bottom-up. Start the design from the business workflow, then the user’s experience, then the logic, then the data. Build the other way, in thin slices: data, then logic, then screen, with enough real data and real connections to test where one piece hands work to the next. A working screen alone proves nothing.

When an agent builds those slices, the work item becomes its input. A user story or a task with clear acceptance criteria is something an agent can build and a person can check. So when the agent produces exactly what the ticket says and the result is useless, inspect the ticket, not the agent. Bugs, change requests, and incidents are the signal that the specification was wrong.

Lesson: spend your attention on what is expensive to reverse. Let the agent spend its tokens on what is cheap to throw away.

Go deeper:

Counting the cost of owning it

A yes to the first four questions still says nothing about money. The next question is the one most budgets get wrong, because they price the build and forget the years of running it.

5. What will it cost to own, not to build?

Here is the trap inside the word “cheap.” In 1865 the economist William Jevons looked back at a century of steam engines that kept getting more efficient, while some experts expected better technology to make England burn less coal. It burned more, and he explained why: cheaper coal found more uses, and demand grew faster than efficiency. His line still applies: “It is a confusion of ideas to suppose that the economical use of fuel is equivalent to diminished consumption.”

Code behaves like coal. When a feature costs twenty minutes, we ask for twenty features, and every one still has to be read, run, kept working, and understood. Dijkstra said in 1988 that we count lines of code on the wrong side of the ledger: they are not “lines produced” but “lines spent.” The Decision Framework’s capability model puts it in two short sentences: “Building got cheap. Owning didn’t.”

The same page pictures every agent as a coin. One side is the demo: visible, interactive, easy to show in a meeting. The other side runs in the background with nobody at the keyboard, and that side is what changes the operating cost. The demo gets the project approved, but the other side is what you own, so budget the two separately. The evaluation criteria page counts the cost of owning across licenses, usage, and engineering hours, and adds two warnings that are easy to miss. A system that charges per call quietly tempts you to test less, so budget the testing as its own line. And an agent in a loop can spend a month’s budget in a few hours, so set spending caps before launch.

The side you seeThe side you own
The demo in the meetingThe job that runs with nobody at the keyboard
One happy caseThe odd cases, retries, and exceptions
The cost to buildThe cost to run: usage, checking, fixing, and the owner’s time
“It works”The cost of one outcome that met the standard

The last row of that table is the number to aim for: the total cost of one outcome that met the agreed standard, with the checking and the fixing included. Count only the cases that met the standard. Keep the rejected and unfinished ones visible, or dropping the hard cases will make the average look good. To estimate that number, the official design principles name what drives it: how much data, how many questions, how much load at once, and the hidden cost of the services you depend on. One more correction belongs in every business case. Staff time freed by AI is capacity, not cash. It becomes a saving only if spending actually falls, or if someone names what the freed hours will now do.

Lesson: price the side of the coin nobody watches. Cost per good outcome, checking included, build and run budgeted apart.

Running the pilot and measuring it

With the cost understood, the idea can meet real work. A pilot has to answer two questions in order: can it survive daily work, and did it make anything better?

6. How do we run the pilot?

A pilot is not a demo. A demo shows that something can work once. A pilot finds out what it costs to work every day. The official planning guide gives a shape worth following: pick a high-value case that matches the skills you actually have, start with internal work that does not face customers, and use what the pilot teaches you to estimate the real timeline. It also says to add a buffer for learning and surprises.

The agent business plan adds the rule that is the whole point of a pilot: “Pilot the hardest steps.” If the agent succeeds there, the easy steps will follow. If you pilot the easy steps, you learn nothing you did not already know. The same page says to use business numbers to decide, at each stage, whether to go on or stop, and to make that choice “based on the data, not assumptions or optimism.”

A choice based on data needs rules written before the data arrives. So before the pilot starts, write three things down: what result would make you expand, what would make you change the design, and what would make you stop. Before anyone looks at results, also decide which cases you test, how long you watch, and which failures you will not accept. Then run the pilot on real cases, including the awkward ones. Bring the people who will own it afterward into the room from the first week.

The Decision Framework’s implementation patterns make one more point. Most real systems start in one shape and move to another as the requirements settle, so plan the move. A pilot that cannot grow into the real thing teaches you less than it seems.

Lesson: pilot the hardest step, on real cases, with the stop condition written before you start.

Go deeper:

  • Plan for AI adoption: proof of concept. Explains how to pick the first case, why to start internal, and how to turn pilot results into an estimate.
  • Business plan for AI agents: success metrics. Shows where to place decision gates between stages, and how to keep measuring after launch.
  • Implementation patterns. Describes the common starting shapes and the signals that tell you it is time to move to the next one.

7. How will we know it worked?

If AI made the work cheaper, we should be able to show where the time went. Usually we cannot, because we trust how it feels.

In early 2025, METR randomly assigned real tasks to experienced open-source developers, with and without AI. They finished about a fifth slower with AI. They believed they had been about a fifth faster. Same people, same work, opposite numbers. In its February 2026 update, METR says developers likely get more help from AI than they did in early 2025, but its own data cannot yet say how much. Other studies find real gains, but only for some people and some organizations, as the table below shows.

StudyWho was measuredWhat it foundWhat I take from it
METR, early 2025Experienced open-source developers on their own projects, tasks assigned at randomAbout a fifth slower with AI, while believing they were a fifth fasterFeelings are not measurement
METR, February 2026A larger group, same designLeans toward a speedup, but too noisy to be sure: “only very weak evidence”When people refuse to work without AI, the measurement itself breaks
Generative AI at WorkOver five thousand customer support workersMore issues resolved per hour, with the gain mostly for the newest workersFor individuals, AI can be a leveler
DORA 2025Software organizationsAI amplifies what is already there: a strong system gets stronger, a weak one is exposedFor teams, the system around the tool decides the result

None of these is a number to paste into a business case. The studies do not agree, and that is the point. Together they give one instruction: measure in your own setting. Compare against the baseline from question 1, using similar cases with and without the tool. Look at the slow cases, not just the average. Give delayed failures time to appear. Count total human effort, time to the final outcome, quality failures, and cost. One habit matters more than the rest. Most teams track cost, time, token use, and tickets closed, but few check whether the output is right. Check the progress, not just the bill.

Lesson: faster is a measurement, not a mood. If you cannot show where the saved time went, you have not saved it yet.

Controlling risk: authority and safety

A pilot that works raises the next question: how far should the system be trusted once it is live? Risk comes in two parts. One is authority, meaning what the system may do on its own. The other is safety, meaning what it can reach and how it can be attacked.

8. How much may it do alone, and who answers for it?

The capability model separates three levels of trust: the system recommends, it acts within set limits, or it owns the outcome. The line between the first two is where accountability changes hands, and that line is the real design decision. The page says it in one sentence: “Capability is a demo. Authority is a liability.”

The official agent governance guide draws the same line and gives it a name: the assist-to-execute line. An agent that drafts a reply assists a person who stays in charge. An agent that sends the reply, updates a record, or moves money makes a change in a system the business treats as the truth. The guide’s rule is short: “Sort every agent by what it does, not by how impressive it looks.” It then sets three risk tiers, and each tier adds controls to the one before it.

Risk tierWhat the agent doesWhat it needs before it ships
LowSummarizes, drafts, or searches for one person or a small teamA named owner, basic monitoring, a release checklist
MediumAnswers domain questions or runs an internal service where a wrong answer misleads peopleAll of the above, plus an expert who confirms the answers, monitoring of the knowledge it reads, and a formal gate before going live
HighSits in a core process, faces customers, or takes consequential actionsAll of the above, plus a process owner, a security and responsible-AI review, written decision rights on what it may decide alone, an incident plan, and a regular review

The tier sets the controls for the whole agent. Inside it, decide per action what the system may do. Reading can be logged. Writing needs a person to confirm. Anything destructive needs approval through a separate channel, from someone who owns the process. The Decision Framework asks for a named owner for every production duty. A useful split is two owners: one for the business result and one for keeping the service alive. The Decision Framework’s decision method page gives the final test: “An agent you cannot see, attribute, or switch off is not in production.”

Owners need rules to work inside, and that is where leadership comes in. The official strategy page keeps it to three moves. Leaders say what AI is for and how they will measure it. One central group writes the rules that apply to everyone, so each team does not invent its own. Everyone gets access, plus training, because the people doing the work are the ones who will spot where AI helps.

The Center of Excellence guide names the three ways that central group fails: the gatekeeper who reviews everything and enables nothing, the ghost that exists on paper only, and the perfectionist who will not let anyone ship until governance is complete. The same guide’s risk page answers all three: “Governance is never finished. Compliance is continuous.” Publish the guardrails, let teams build inside them, and refine as you learn.

None of this limits the technology. It is how the project survives its first bad week. AI informs. Humans commit.

Lesson: decide which actions it may take alone, which need a person, and who is named when it goes wrong. Before launch, not after.

9. How do we keep it safe?

For safety, the oldest security rule still carries the most weight. In 1974 Jerome Saltzer wrote that every program and every privileged user should operate with the least amount of privilege necessary. An agent is a program that acts on behalf of a person, so it must see only what that person may see, and do only what that person may do. The Decision Framework’s decision method page separates two things that get confused: an agent’s attribution, meaning who it acts for, and its data access, meaning what it may reach. They are different problems, and both need solving.

Least privilege limits the damage. The next step is to know the attacks. Microsoft’s official security guidance starts with the list of attacks you already defend against. It then checks that list against the AI-specific attack catalogs kept by MITRE ATLAS and the OWASP generative AI project. The new attacks have names worth learning. In prompt injection, a document or a message the agent reads carries instructions it was never meant to follow. In data leakage, sensitive data escapes through the answer itself. In model inversion, an attacker pulls training data back out of the model. The page’s advice is to red-team the system, meaning attack it on purpose before someone else does, and to repeat that as models and usage change.

A manager does not need every attack name. They need answers to four questions, which turn the final test from question 8 into checks. Is there an inventory of every agent, with an owner? Does each agent have its own identity, so an action can be traced to it? Are the data boundaries written down, so the agent cannot reach what the requesting person cannot? Who can switch it off, and how fast? The governance page turns Microsoft’s six responsible-AI principles into six risk questions, shown below. The accountability one is the sharpest: where could it be unclear who is responsible?

PrincipleThe question to ask about this project
Privacy and securityWhere could it handle sensitive data, or be attacked through what it reads?
Reliability and safetyWhen could it fail to work safely, or give an answer nobody should trust?

The business plan page has the line that closes this conversation: “If you can’t name the risks, you can’t manage them.” Pause until you can.

Lesson: least privilege, an identity per agent, a written data boundary, and a switch someone is allowed to pull. Name the risks or do not ship.

Controlling quality: checking and drift

Risk controls stop the system from doing harm. They do not make its output good. Quality also has two parts: someone has to check the output before it is trusted, and someone has to notice when it slowly gets worse.

10. Who checks the output, and is that capacity planned?

Dijkstra, 1969: “Testing shows the presence, not the absence of bugs.” That was true when a human wrote every line. It matters more now, because an agent can pass every check we thought to write and still miss the reason the ticket exists. The Decision Framework’s scenarios page says it in one breath: “Generation got cheap. Verification did not.” Geoffrey Huntley, asked what is left when nobody types code by hand, answers: vision, verification, and agency. Two of the three are about checking.

So what counts as checked? The test for “done” is simple: the next person can do their job with the output. Say we build a tool that summarizes support tickets. The summaries are clear and complete. Then an engineer notices one left out the customer’s software version and mixed up a fix that was tried with one that was only suggested, so they reread the whole conversation. We shipped a feature, and the workflow gained one more document to check. “Done” is decided by whoever receives the output, not by whoever produces it. Build the proof there, with the receiver, on real cases.

The official evaluation checklist turns this into steps a team can follow. Start with one test case per key scenario, each with a prompt, an expected answer where one exists, and a written rule for what passes. Run it, record the pass rate and the version, and dig into every failure: is the test wrong, or is the agent wrong? Then widen the set to cover rephrased questions, edge cases, and the things the agent must refuse. Because outputs vary, run the set several times and aim for a realistic pass rate rather than a perfect one. The checklist suggests 80 to 90 percent, set by what the business needs.

The Well-Architected testing page adds a distinction that is easy to blur: evaluation finds the best model during development, and testing checks the whole system every time anything changes. Both need trusted examples checked by humans. The page calls the evaluation set the golden dataset, and it advises keeping the two sets separate.

A test set does not run its own reviews, so plan the checking as work, with people and hours. If an agent opens forty changes a day and the team can honestly review ten, the extra thirty are a pile going stale in a queue. Through a Senior’s Eyes works through the same arithmetic: more workers do not make the one person who decides any faster. Sprints assumed building was the slow part. If review and decisions are now the slow part, plan the sprint around what the team can finish and check, not around how much the agent can generate.

Even a well-staffed review can fail slowly. Diane Vaughan studied the Challenger disaster and named the normalization of deviance: each time a check is skipped and nothing goes wrong, skipping becomes a little more normal. An agent that has been right ten times is the perfect setup, and the eleventh review is the one you will want to skip. The Decision Framework’s page on engineering with agents names the same risk and reduces the whole debate to one question: “can you prove it works?”

Lesson: define done by what the next person can do with it. Budget the review. Keep reviewing after it has been right ten times.

Go deeper:

  • Test and evaluate AI workloads. Separates evaluation from testing, explains golden datasets, and shows how to test agents that call tools.
  • Engineering with agents. Argues for verification over reading code, and shows how to split review when no engineer is in the loop.
  • Software should be explainable, not readable. Huntley argues that types and checks should push back on bad output, and that “porting is easy when the end result is easy to verify.”

11. How do we keep it good after launch?

Reviews are not the only thing that decays slowly. Meir Lehman, with Laszlo Belady, began writing down in 1974 what every operations team learns the hard way. His first law: a system that is used must be continually adapted, or it becomes progressively less satisfactory. By 1996 the list had grown to eight laws, and the seventh says a system’s quality will appear to decline unless it is rigorously maintained. He was writing about ordinary software. AI systems obey his laws faster, because the world the model learned from keeps moving and the model does not.

The Well-Architected testing page names the two ways this happens. In data drift, the inputs change, so a model trained on last year’s cases misreads this year’s. In concept drift, the world changes, so the right answer changes while the model keeps giving the old one. Either way, the system that passed its pilot is slowly becoming a different system.

So launch is where the measuring starts, not where it ends. The official management guide asks for four things. Know what good looked like at launch. Keep the golden dataset current and rerun it on a schedule. Make every new model version pass a check before it reaches production. Keep a calendar of model retirement dates so a vendor change does not surprise you. The evaluation checklist lists the events that should trigger a full rerun of the test set: a model change, a major update to the knowledge the agent reads, a new tool or connection, and any production incident. Microsoft’s observability guidance adds checking a sample of real production answers and scheduled red teaming, so you find the drift before the users do.

graph LR
    T["Build a test set<br/>one case per key scenario"] --> B["Record a baseline<br/>pass rate and version"]
    B --> W["Widen it<br/>rephrasings, edge cases, refusals"]
    W --> L["Launch<br/>sample real traffic"]
    L --> E["A trigger fires<br/>model change, knowledge update,<br/>new tool, incident,<br/>and my addition: a rejection"]

That list of triggers needs one more entry: a rejection. The receiving step needs a way to reject the output, with a reason such as a missing version, an unsupported conclusion, the wrong customer, or a stale policy. Those reasons should travel back to the step that produced the output. A rejection is the cheapest signal of drift you will ever get. The people who use the system need the same power: a one-click way to say the answer was wrong, and a real way to contest a decision that affected them.

Lesson: the system you launched is not the system you will be running in a year. Rerun the tests on every change, and listen to the rejections.

Applying the questions to five kinds of delivery work

The eleven questions stay the same from project to project. Their answers do not, especially in software services, where a vendor builds for a customer and the same work can be sold in different ways. A dedicated team billed by the hour, a maintenance contract, a fixed-bid project, a migration, and a sales pursuit each get a different answer to the question that decides the rest: when AI saves an hour, who keeps it? Whoever keeps the saving is the one who wants to measure it. Whoever carries the risk is the one who has to check the output.

What follows is a general pattern. No customer, project, or person is named, and no real contract numbers are used.

Five ways delivery work is sold

If you have only built products, these words may be new. Here is each one in plain terms, with the flow of work it usually follows. A dedicated team sells effort. Maintenance sells a running system. A fixed bid sells a result, and a migration sells a safe move to a new platform. Presales sells a promise.

A dedicated team billed by time is often called an ODC, an offshore development center. The vendor keeps a stable team that works only for one customer, often for years. The customer sets priorities from its backlog, much as it would for its own staff, and pays by hours or by headcount at an agreed rate. This is time and materials: the customer buys effort, not a result. The team gets work, delivers it in short cycles, and reports the hours.

Maintenance and support, often called AMS for application maintenance and support, keeps a system running after it goes live. The work arrives as tickets: questions, incidents, and small change requests. A service agreement fixes how fast each kind must be answered and solved. Support is usually split into three levels. Level 1, the service desk, receives every request, sorts it, answers known questions from a knowledge base, and passes on what it cannot solve. Level 2, application support, investigates incidents in logs and data, finds a workaround, records the known error, and decides whether code must change. Level 3, development, changes the code through impact analysis, design, fix, test, and release, and the customer’s change requests land here too.

The vendor estimates up front and carries the risk: if the work takes longer, the vendor pays the difference. Anything outside the scope becomes a change request with its own price. The work usually follows the familiar sequence of requirements, basic design, detailed design, code, unit test, integration and system test, and acceptance, with a review gate at each step.

The old system is the specification: whatever it does today, including behavior nobody wrote down, the new one must do or deliberately drop. Two patterns come out of that table. First, the more a machine can check the output, the more work AI can safely take. A migration has an old system to compare against, so it can use the most. Presales has no test suite for a promise, so it should use the least without a person in the loop. Second, the activities share their foundations. One knowledge layer with permissions, workflows for fixed steps, a coding loop with an independent checker, and a way to watch production serve all five. Build those once and each activity is a configuration, not a new project. The sections below take the five in turn.

Dedicated teams billed by time

The trap here is simple. If the customer pays for hours, every hour AI saves is an hour nobody bills. The vendor has no reason to measure, and the customer has no proof to ask for a better deal. Most teams do use AI, but “not measured yet” is their most common status. Question 7 is the bottleneck, not the tool.

The way out starts with the work, not the contract. Split the work before you change the price. Some tasks are repetitive, and their output can be counted. Some are semi-structured and can be measured through engineering signals. Some are exploratory, and their outcome cannot be defined in advance. Only the first kind can move to pricing by outcome. Saying openly that exploratory work stays on hours is what makes the other definitions believable.

Then measure in the shadow before you change anything. Keep invoicing as today and calculate in parallel what the new model would have charged. That gives the comparison question 7 asks for, at no risk to either side. When the numbers hold, move one step at a time, from committed capacity to shared savings to outcome pricing, and gate each step with data from the one before. Write the way back in advance too, for example a return to hours after two quarters of missed targets. That is question 6 applied to a contract.

Pricing is not the only thing that can stall a team. Each customer’s AI policy is the data boundary: one customer allows code, another allows only documents you send them, a third allows nothing yet. Keep that list per project and check it before every new tool (question 9). And budget the tool quota as a cost of owning, because teams stall when credits run out mid-month. That belongs in question 5, not in a complaint.

Maintenance and support

Maintenance is where AI should pay first, because the outcome is already countable: a ticket closed to the agreed standard. The closed tickets are also a free test set. Mask the personal data in a year of closed tickets and you have a golden dataset of real cases with known answers, ready for question 10. The same history gives a safe pilot for the hardest step. Replay impact analysis on closed change requests and compare the agent’s list of affected parts with what actually changed. It is internal, cheap, and it tests the part that matters (question 6).

Not every step needs a model. Sorting tickets is a workflow, and so is the monthly service report, whose numbers must come from a query, never from a model. That is the rule from question 2. Where a model does help, define done where its work lands. For sorting, done means the ticket was not re-routed. For an answer, it means the customer did not ask again. For an investigation, it means the real cause was in the agent’s top three. Those are the receiver-side measures from question 10.

The tickets that make a good test set are also the main risk, because every ticket is untrusted input. Customer emails, logs, and attachments are exactly where a hidden instruction can enter, so agents that read them start read-only, and every write needs a person (questions 8 and 9). A second risk is quieter: the team slowly stops understanding the system. Maintenance is where the theory of a program lives. Peter Naur used that word for the understanding in people’s heads that lets them change a program safely (see the personal notes below). If an agent writes most fixes, ask each fix to explain why, not only what, and rotate people through the hard modules.

Fixed-bid projects

Here the vendor keeps the saving and also carries the risk, so the questions about cost and checking come first. Price only the savings a pilot has proven. Everything else is a forecast and should be written as one, with its assumptions, a confidence level, and a trigger for re-estimating. A price cut based on an unproven saving is a loss the vendor pays for later.

The estimate itself needs three lines: building the AI support, running it, and the human hours to review and fix its output. The third line is the one most often forgotten, and it is where a good-looking productivity number turns into a late milestone (questions 5 and 10). It is also why the review queue belongs on the project dashboard. The first sign of trouble is not a slow agent. It is a growing pile of output nobody has checked.

Two older lessons still apply. Jevons applies to scope: when the customer hears how fast the agent is, more features appear, and every out-of-scope request still goes through a change request. Naur applies to the end of the contract. A fixed-bid project usually ends in warranty or maintenance, so name who will hold the theory after delivery. If nobody understands the code the agent wrote, the warranty is where the saving is paid back.

Migrating an old system

Migration looks like the perfect AI job: a large amount of mechanical translation. Migration is a harness argues that the naive version, legacy code in and modern system out, fails. What works is a loop built around the model. Before that loop runs, each component needs its own decision: rehost, replatform, refactor, replace, retire, or retain. Different components get different answers, and that is healthy.

The judge comes first. Because the old system is the specification, correct means behaving like it. That behavior can be captured as an inventory of business rules, golden outputs, recorded user flows, or a harness that runs old and new through the same surface and compares them. Anthropic’s code migration kit puts it in one line: “No judge, no exit condition.” This is question 10 in its strongest form.

The order of work follows question 4. Move the data before the logic: settle the data model first, then grow the new system around the old one through seams, unit by unit, as in Martin Fowler’s strangler fig. The first unit is the easiest one, because its job is to prove the pipeline and the judge, not the hard cases. Inside each unit, separate the one who writes from the one who checks. A planner hands out one unit at a time. An orchestrator runs a generator and an independent evaluator until the unit passes. Each passing unit becomes one commit, so a failed attempt is a clean reset away. The public Bun port to Rust used the same shape at a million lines, with reviewers that saw only the diff and were told to find what was wrong.

When failures repeat, fix the process, not the file. A failure seen once gets a fix. A failure seen three times means a rule is wrong, so change the rule and regenerate what it touched.

Cost is counted against the judge too: per unit proven equal, not per line produced. Then match the model to the role: a cheaper model that needs five loops per unit costs more than a capable one that needs one (question 5). The last risk is the one the code cannot show: modern legacy. Code-only modernization can produce a new system that nobody understands, which iSAQB calls a real risk. The understanding has to migrate too.

Business development and presales

Presales is the one activity where the output cannot be tested before the customer reads it, so the questions about honesty matter most. Sell the questions, not the tool. The strongest offer is often not a tool at all. A discovery workshop that answers questions 1 to 4 with the customer is worth more than a demo, and it is the start of a project you can actually deliver.

Every claim in a proposal needs your own measurement behind it. Do not paste a study’s number into a proposal as a promise, because question 7 shows the studies disagree. Show what you measured in your own delivery, with and without the tool. The same goes for people: selling AI-augmented engineers at a higher rate needs proof of how they check AI output, not a certificate that they used it. Governance is evidence too. A customer who is asked to move from hours to outcomes needs to see how the vendor measures, reviews, and switches things off. Dashboards and review discipline are what make outcome pricing believable.

Finally, keep customer material inside the boundary. Requirement documents and source code shared during a pursuit fall under question 9 like any other data. Drafting a proposal is a tier 1 task in the terms of question 3, but the documents it reads may not be.

Personal notes on the work that is left

I think there are two common kinds of work today: building the agent system, and building the context system around it. They are the shared foundations the five kinds of delivery work stand on: a loop with an independent checker, and one knowledge layer with permissions. The eleven questions are the job of whoever signs off on a project. These two notes are about the people who build those foundations, and how they keep up. They lean on older thinkers than the Microsoft pages.

Two kinds of work: the agent system and the context system

The first kind, the agent system, is about making the agent itself handle more of the task. That means four things: it runs longer without stopping, it survives failures, it spends less for the same result, and it takes on harder work. All four depend on something that has to come first: a target the agent can be checked against. Without a check, a longer run is just a longer way to be wrong, and a cheaper run cannot show that it still gives the same result. With a check, you can cut the steps and the cost, and prove the result stayed the same. This is an old discipline under a new name. Martin Fowler’s Refactoring (1999) describes refactoring as a series of small behavior-preserving transformations. Only a test can tell you the behavior was preserved. Making an agent faster or cheaper is a refactoring of the work itself. The test set from question 10 is what makes it safe.

The second kind of work is building the context system. The information the agent gets must be consistent, current, relevant, and just enough. It must also stay inside what the person asking may see, the rule from question 9. Connecting the tools, such as the issue tracker, the chat, and the document store, is only the starting point. The hard part is knowing where each fact came from, when it was valid, and which version applies. The model does not fix bad data. It combines what it is given, and it is very good at that, so most of the engineering is in what it is given. The model is the part you can rent. The context is the part nobody can sell you.

A context system also grows with the organization, and the hard problem changes at each step:

SettingWhere the context livesThe hard part
Solo developerThe repository, an instruction file, a folder of notesThe discipline to write things down
Small businessA few shared tools: chat, documents, an issue trackerKnowledge lives in people’s heads, so you need one shared truth
Manufacturer with a thousand peopleOffice tools plus the plant systems, machine data, and procedures, often on paperThe documents say one thing and the factory floor does another

The amount of data grows down that table, but that is not the real change. The hard problem moves: from discipline, to shared truth, to the gap between documents and reality, to permissions, to shared meaning, to law and language. Adding more documents to a search index does not settle any of those.

Under every row of that table sits one more layer of context, and no tool holds it. In 1985 Peter Naur wrote Programming as Theory Building. His claim is that the program is not the code. It is the theory in the heads of the people who built it: the knowledge that lets them explain it and change it without breaking it. Then comes his sharpest line: “The death of a program happens when the programmer team possessing its theory is dissolved.” A dead program keeps running. You find out when someone asks for a change and nobody can answer.

When an agent writes the code, nobody holds the theory by default. Geoffrey Huntley argues that software no longer needs to be readable, only explainable by a model on demand. I think that is half right. An explanation on request is useful, but it is not a person who understands the system and answers for it. The instruction files we now write for agents, a CLAUDE.md or an AGENTS.md, are the theory partly written down: what the system is for, which decisions were made and why, which source wins when two disagree. That is where the context system and the theory meet. It makes these files the most valuable documents a team can write today. They are still not the whole theory.

Michael Polanyi explained why in 1966, in The Tacit Dimension: “we can know more than we can tell.” You recognize a face without being able to say how. A senior knows which module is fragile and cannot write the full reason down. Every instruction file holds the part of the theory that could be told. The part that could not is still in someone’s head, and it is often the part that matters when the system breaks. Someone has to hold it, and that person’s time is part of the cost in question 5.

Lesson: give the agent a target it can be checked against before you make it run longer or cheaper. Write the theory down, for the agent and for the next person. Name the person who will still understand the system in a year, and give them time to keep understanding it.

How do we keep learning?

Both kinds of work run on tools that change every month. Problems and patterns do not. Learn the core idea behind a tool, how it is built, and where it stops working. Then you can judge the next ten tools built on the same idea without trying them all.

Choosing what to learn needs a checklist, in this order: what it does, the core idea, the cost, the license, whether it fits a need you actually have, and only then how popular it is. The useful core often does not look fancy. Learning it then needs a little practice every day: one small question for ten to fifteen minutes, such as sketching a system design for a requirement you have not seen before. Nobody can work on a large codebase every day, but small practice adds up. It also prepares you for the interviews and reviews where someone asks you to think out loud.

Sources can come from anywhere: professional networks, paper feeds, repositories, release notes. The rule is to follow the links before trusting the summary, because several posts copying one announcement are still one source. An earlier post on this blog, How to learn?, puts it in one line: qualify what you learn before you learn it.

Why so little, so often? Richard Hamming answered that in 1986, in a talk called You and Your Research. He had spent years at Bell Labs watching which scientists did work that lasted, and asking why most did not. One of his answers had nothing to do with talent. He passed on a line from his colleague Hendrik Bode: “Knowledge and productivity are like compound interest.” Hamming’s example: of two people with about the same ability, the one who works ten percent more will more than twice outproduce the other. Over a career the gap keeps growing, because each thing you understand makes the next one cheaper to learn.

Agents raise the interest rate. They can summarize anything in seconds, so the only thing that still compounds is your own understanding. The danger is accepting the summary without doing the work of understanding. Hamming also noticed that the people who worked with the door open got interrupted more, but “occasionally” picked up clues about what might be important. He said he could not prove cause and effect, only a good correlation with doing important work. That is a good reason to read widely and keep the door open, as long as the fifteen minutes still happen.

Lesson: learn the idea, not the tool. Check the source before you learn from it. Fifteen minutes a day beats a long list of names you recognize.

  • Through a Senior’s Eyes. An earlier post on this blog about what changes in how a senior sees a problem, rather than what they know.

Two questions I cannot answer yet

Both notes rest on things I cannot prove yet. The learning note treats the urge to understand as a human strength. The context-system note assumes the agent is fed in natural language. So two questions remain: is curiosity part of intelligence, and could an agent work in a language built for its domain?

Is curiosity part of intelligence?

In October 2026, an AI lab released 722 papers claiming results on major open problems in mathematics. Three were withdrawn within a day, and experts expect checking the rest to take months. The same week, Terence Tao gave a talk he had planned long before, Math 2.0. It is not about whether these proofs are correct. He describes the present as shaped by “the excessive emphasis on automated solving of open problems by AI.” He asks for a future where AI is used to support the mathematical community and the understanding that connects mathematics to the real world. In his living summary of his views on AI, and in earlier remarks reported secondhand, he worries that mass solving leaves a field “much less fertile”: the answers exist, but nobody does the follow-up work that a hard problem usually sparks. His complaint is about the incentives around AI, not the tool.

His slides pose a thought experiment: an AI finds a cancer cure that passes its clinical trial and comes with a machine-checked certificate, but nobody knows how it was found. Would you want at least one human expert who understands the mechanism, even partially, before the injection? That is Naur’s question again, asked about a whole field.

Tao’s concern points at something people do without being asked. When a person reads or builds something, questions show up that nobody assigned. Something bothers them, connects to an old idea, or makes them wonder what happens if an assumption changes. They keep thinking about it after the task is done. That is part of what I mean by human intelligence.

A model can solve a hard problem and produce good follow-up questions. Asking it to act curious produces more of them. But those outputs alone do not tell me whether anything matters to it beyond the task we gave it.

The question is also harder than it looks, because curiosity can already be built as a reward. Around 1990, Jürgen Schmidhuber described artificial curiosity: a learning system rewarded for finding what its own model of the world cannot yet predict, and later for how fast its predictions improve. Systems built this way explore without being told where to look. So the test cannot be whether a machine seeks out the unknown. It has to separate solving the question in front of you from finding something you want to understand even after nobody is asking. What could I observe that would tell the two apart? I do not know how to test that yet.

Could an agent work in a language built for its domain?

Natural language is a rich input. A vocabulary and a grammar let us express facts, logic, relationships, and ideas nobody has written before. That flexibility helps models connect ideas and produce useful, sometimes beautiful things. But the same language carries assumptions, biases, contradictions, fiction, and lies, and learning from it does not by itself teach a model which claims to trust. This is part of the hallucination problem, not a complete explanation of it.

An autonomous agent’s main job is to solve problems and act. Conversation helps when it works with people, but it does not have to be the representation for every step inside the system. So my question is this: could an agent learn and operate directly through a language built for its domain?

By a domain-specific language (DSL), I mean domain concepts with defined meanings, operations, types, and constraints. Mathematics has formulas and proof steps. A machine has states and allowed transitions. A robot has sensor readings, positions, velocities, and control signals. An agent acting in an environment also gets the effects of its own actions as input. Each of these can express a great deal within its domain without carrying all the ambiguity of everyday conversation. JetBrains’ MPS FAQ gives a short introduction to how such languages define their concepts and the rules that constrain them.

The model could still be probabilistic. The input would simply leave less for it to guess. Compare “the machine seems too hot” with a reading of 105°C against an operating limit of 90°C, from a sensor marked valid. The second makes the measurement and the threshold explicit. Choosing an action may still need more context, but the agent no longer has to guess what the speaker meant by “too hot.”

One terminology note, because the words are easy to confuse. Meaning that depends on context is not the same as a context-sensitive grammar in formal language theory. Stuart Shieber showed in 1985 that some natural-language constructions go beyond context-free grammars, but that does not mean natural language needs unrestricted grammars. My concern is implicit meaning and ambiguity, not where language sits in the Chomsky hierarchy.

A DSL is also more than asking a model to return JSON. A JSON field can still hold ambiguous prose or an unsupported claim. I mean the representation the agent learns from and reasons with: observations kept apart from assumptions, explicit units and uncertainty, and actions whose requirements and effects can be checked before they run. Natural language would still connect human intentions to that system.

The DSL idea itself is old, and so is its cost. In the 1600s Leibniz dreamed of a universal symbolic language in which a dispute could be settled by calculation instead of argument. Three centuries later, the expert systems of the 1980s tried a smaller version: domain knowledge written down as explicit rules. They were precise inside their vocabulary and brittle the moment a case fell outside it. A DSL for agents would face the same trade: what the language leaves out, the agent cannot handle. So it needs a way to represent the unknown or to ask for help.

A DSL also would not remove false data, bad assumptions, or model errors. It could make some of them easier to catch before an action runs.

So the open question is whether we can keep enough expressive power for new combinations and useful reasoning, while making meaning explicit and actions easier to check. Could a language like that support an agent’s ability to learn, reason, and discover? I treat the DSL idea as a hypothesis to test, not a claim that changing the language makes a model reliable.
