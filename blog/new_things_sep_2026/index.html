Interesting Things I Found — Sep 2026

Last month I said the org chart around the coding agent was filling in, seat by seat. This month something different happened. Several teams shipped the same new kind of model, and it isn’t an agent at all. It doesn’t write. It doesn’t chat. It looks at a situation, looks at the options you give it, and picks one, with a probability attached.

Most of them use the same name for it: System One. It’s the old idea from psychology. You have a fast, cheap, gut-feeling brain for quick judgments, and a slow, careful one for hard thinking. For three years we’ve used the slow brain for everything, even for questions like “is this a billing complaint?” This month the fast brain showed up as a product.

So that’s where this post starts. After that comes a harness that learns from its own runs, a memory that forgets on purpose, and models that read raw bytes. Then the machines, searches, and teams around all of it.

Twenty-one finds, six groups.

1. The fast brain — models that decide instead of talk

Seven links in six entries here. The surprising part is how much they agree.

  • CLM — Contrastive Language Models — the most “under the hood” of the batch. CLM doesn’t generate an answer. It embeds the state and each candidate action separately, then scores how well they match. A softmax over those scores gives you a distribution. Each encoder is a frozen LLM backbone with a small trainable head on top. Training is contrastive: pull the right state-action pairs together, push the wrong ones apart. Because states and actions are embedded apart, you can cache them. A state you’ve seen before is cheap to ask about again. It can also rank free-form candidates, like best-of-N answers or tool names. There’s a script to fine-tune the heads on your own data. Code and weights are Apache 2.0. Honest notes: it’s text-only, and the default context is short, so longer states get cut. The benchmark numbers are the project’s own, and the scaling write-up lives in a blog post, not a peer-reviewed paper. Best for: seeing how a decision model is actually built.

  • TypeSafe AI and its agent skill — the product version of the same idea, built around their main model, Jev. You send state (your data, as text or JSON) and a list of typed questions. Three types cover most needs. Choice picks one from a set. Noul answers yes or no, as a probability. Score places the state on a scale you describe. Every question is answered in parallel and on its own, against the same state, so one question can’t leak into another. Answers come back as values your code can branch on. No text, no parsing.

    The skill file is worth reading even if you never use the product. It’s really a design guide for this new kind of AI feature. Work backward from what the app will do. Keep rules, math, and exact lookups in code, and ask the model only for the judgment. Ask one narrow question per dimension. Always include a no-match option, because the model can’t pick an answer you didn’t list. And one warning I liked: high confidence means the answers are concentrated on one option. It does not mean your whole workflow is right. So set thresholds on your own data. Honest note: the docs read like marketing. And when you split a decision into small questions, you have to write the logic that combines them yourself. Best for: turning a fragile prompt-and-parse step into a typed decision.

  • Laya — a local decision engine with the same three question types: choice, noul, and score. Its Router selects a checkpoint for the request, including a multilingual one advertised for 100+ languages. Imagine a support ticket saying, “You charged me twice; refund it or I’ll cancel.” One call can pick the department, rate the urgency, and estimate cancellation risk. Your application gets values it can act on without asking a chat model to write and then parsing its answer. It supports batches and schema-shaped output too. The project benchmarks report about 33 ms for one question on a T4. That’s one measured GPU setup; the higher typed-decisions accuracy also belongs to a fine-tuned checkpoint, rather than the base English model.

    The lesson I liked most is in its failures. The English checkpoint can be confidently wrong on non-English text. A confidence threshold alone won’t catch that; choosing the appropriate checkpoint has to come first. The README also acknowledges overconfidence in the shipped probabilities and truncation of long inputs unless you handle them explicitly. So the practical loop is: route, evaluate on your own labeled decisions, calibrate, then choose which answers may trigger an action. Returning a valid option solves the output-format problem. Measuring when that option is right is still your job. Apache 2.0. Best for: trying typed decisions locally, especially across languages.

  • Strands Decider — the open, local version. It’s a small open-source decision model from the Strands team, with code, training data, and weights all published. The build is simple to explain. Take a pretrained LLM, cut off the part that writes text, and put a tiny “pointer head” in its place. That head scores each option you offer, all in one parallel pass. Because it can’t write, it always returns one of your options. It can’t wander off. The blog is honest about the trade: no coding, no chat, no summaries, and weaker than reasoning models on multi-step problems.

    The best part is the agent example. Before a tool runs, a small handler asks the decider two questions. Are these arguments based on what the user actually said? Is it too early to call this tool? Then it returns one of four actions: Proceed, Deny, Confirm (ask a human), or Guide (send feedback to the model instead of blocking). That’s the watcher I keep writing about, small enough to run on a laptop. Best for: experiments, local guardrails, and cheap routing.

  • OpenAI Decisions — and then the biggest vendor shipped one too. It’s a new endpoint, in public beta. It takes text or images plus a list of questions, and returns typed answers. There are three question types: predicate (the probability that something is true), choice, and score. The guide’s examples are everyday cases. Is this product photo damaged? Which department should get this complaint? How bad is this bug? You pay only for input. There’s no output to pay for, because nothing is generated. Honest notes: it’s beta, and it runs on a single model. The guide also says plainly that thresholds are your job. Test against labeled examples, and weigh the cost of a false yes against a false no. Best for: teams already on OpenAI who route, filter, or sort requests at volume.

  • Jev-Mem — a university paper that puts the fast brain inside an agent’s memory. And it isn’t just a similar name: it uses TypeSafe’s Jev as its fast controller. Their complaint is this. Most agent memory systems ask a big, generating LLM how to file, find, and use every memory. So slow generation sits in the way of every memory operation. Jev-Mem splits the work in three. A System-One control plane handles the routine choices: what type of memory this is, where to send a query, how much to retrieve, when to stop searching. A structured graph holds the memories. And a System-Two reasoning plane is called only when an answer needs real thinking. They report better answers and much faster building and querying on their benchmark. Honest note: one benchmark, self-reported, and the abstract doesn’t name what they compared against. Best for: a blueprint of the fast brain and the slow brain working as one system.

The shared shape. Put them side by side and they’ve ended up with almost the same interface. Look at the question types:

OpenAI uses the same three shapes too, and its guide doesn’t mention the others. I can’t tell if they got there alone or not. Either way, the biggest vendor shipped the same three building blocks. That’s a strong hint these three are the right ones.

Why it matters. Most of what an agent does all day isn’t hard thinking. It’s small calls. Which tool? Is this safe? Is this relevant? Is it done? We’ve been paying the slow brain to make every one of them, and then paying again to turn its essay into a yes or no. Decision models make those calls cheap, fast, always inside the options, and with a confidence number you can set a threshold on. The reasoning model doesn’t go away. It becomes the one you call when the fast brain isn’t sure.

One honest caveat for the whole section, borrowed from a project in group 5. Cua’s README says its own “System 1” label is an engineering comparison, not a strict category. That’s the right attitude. These are not little brains. They’re classifiers with a good interface. That’s still a big deal.

2. The harness learns

  • Harness Learning Enables Generalizable Test-Time Adaptation — a paper that treats the harness as the thing to improve. An agent’s behavior depends on the model and its harness. The harness is the program that decides when to call the model, which tools to use, and how information moves. Different tasks need different harnesses, but we mostly write one and leave it alone. Their idea: train a proposer model, with reinforcement learning, to revise a solver’s harness using feedback from running it. The reward is how well the revised harness does. At test time, it keeps improving the harness on a brand-new task, without changing any weights. Harness edits do the job that weight updates do in normal training. The result that matters: the skill carries over to tasks it never saw, and a proposer trained on single revisions keeps improving over several rounds. Honest note: it was tested only on reasoning and multi-hop questions, and the gain from training on whole chains of revisions varies. Best for: anyone who suspects migration is a harness problem, and wants proof the harness can learn.

  • prime-agent — a revisit. I covered it last month for its recursive design and its continual harness. It’s back because it’s the shipped, untrained version of the paper above. Its /refine command reviews a run and makes small edits to the harness, each backed by evidence from that run. It edits the extra prompts, memories, and skill descriptions. It takes snapshots so you can roll back, and it never touches the base system prompt. The README also points to their own arXiv paper on the continual harness, and lists tools for long tasks: /goal objectives, heartbeats and schedules, and automatic compaction. The same warning still applies. It runs model-written Python with your permissions, and it is not a sandbox. Best for: trying harness learning today, by hand, before anyone trains it.

  • ECC — the biggest harness project I know of. It began as “Everything Claude Code”, one person’s folder of configs. Now it calls itself the agent harness operating system: dozens of agents, hundreds of skills, hooks, rules, a shared memory format, and a scanner for your own agent config. Claude Code first, with adapters for a dozen other coding agents behind it. Its motto could be the headline of this blog: “Optimize the context window. Persist everything else.” The pitch is an agent that “plans before it builds, verifies changes with tests, reviews its own work from a fresh context, remembers what matters, and turns repeated wins into reusable skills and workflows.” That fresh-context reviewer is the watcher again: a second agent that never saw the first one’s reasoning.

    The part that belongs here is its continuous learning loop. Hooks record every tool call, because a hook always fires and a skill asked to observe only sometimes does. A small model reads the log in the background and looks for three things: moments you corrected the agent, errors it fixed, and workflows it repeats. Each becomes an instinct: one trigger, one action, the evidence behind it, and a confidence score. Confidence rises when the pattern repeats and you don’t object. It falls when you correct it, when it hasn’t shown up for a long time, or when new evidence contradicts it. At session start only a few of the most confident instincts are loaded. They stay inside their project by default and get promoted to global when the same one appears in two or more projects. /evolve groups related ones into a skill, a command, or an agent. In August I complained that the usual memory table had three boxes and no arrows. This is the arrows. Observations are the episodes, instincts are the rules, evolved skills are the habits. And the decay is the revise step I asked for in the lesson library: a stale rule is worse than no rule.

    Honest notes: the observer is off by default, so most installs get a very large library of skills and hooks, not the learning loop. Past a confidence of 0.7 an instinct is auto-approved, so the agent follows rules it taught itself with no human sign-off. The README admits the full plugin advertises its whole catalog to the model and tells you to install only the parts you need when context matters. That’s a real tension for a project whose motto starts with the context window. Nothing in the repo measures whether the instincts help. Only Claude Code gets the full feature set, the observer gets killed on native Windows, and hooks run shell commands, so read them. Install only from the official sources; the project says copies elsewhere may carry malware. MIT, with a paid hosted app on the side. Best for: seeing harness learning run continuously, today, and seeing how big a harness gets when it only ever adds.

The paper learns how to edit a harness. prime-agent gives you the loop to do it by hand. ECC runs a version of the loop in the background, every session, if you switch it on. Put them together, and the state I keep arguing for isn’t just carried between runs anymore. It’s improved between runs.

3. Finding things — memory, documents, code

  • Selective Forgetting — my favorite kind of paper: one that tests a popular belief and reports that it failed. The belief is that turning conversations into a knowledge graph of entities and relations gives an agent better long-term memory than plain vector search. They built exactly that. At the same retrieval budget, the graph did worse than the flat baseline. It did worst on questions about what the assistant said earlier. Breaking a turn into entities throws away the exact wording those questions need. Then the second half: a forgetting step. It prunes low-value nodes based on how recent they are, how often they’re used, how connected they are, and how old they are. Pruning about a tenth of the graph cost almost nothing in answer quality. The authors are honest about the limits: one small extractor model, one benchmark, and the result is about this pipeline, not graph memory in general. Best for: a reality check. Memory is not intelligence, and structure is not understanding. Sometimes the raw text was the knowledge.

  • PageIndex — retrieval with no vectors and no chunks. It builds a tree index of each long document, like a table of contents. Then an LLM reasons its way down the tree to the right section. The core argument is short: similarity is not relevance. Two chunks can look alike, and only one answers your question. You get answers you can trace, with page references. Local mode runs on your machine with your own key. A cloud mode adds OCR, images, and finer citations. Honest notes: local mode needs text-based PDFs, many extras are cloud-only, and the benchmarks are the vendor’s own, mostly simple lookup questions. Best for: long, structured professional documents like reports, filings, and manuals, where the layout already tells you where things are. Read it next to the paper above. Both say that keeping the document’s own shape often beats cutting it into pieces. It’s the inference layer a knowledge base needs, done as a walk down a tree.

  • tgrep — from Microsoft: grep, but with an index. It breaks every file into overlapping three-character pieces (trigrams). A regex search then only opens files that could match, and checks those in parallel. Run it as a server and the index stays current while you work. Most flags copy ripgrep. It ships MCP tools and hooks for coding agents, and it already powers search inside GitHub’s Copilot CLI. Why it matters for agents: an agent greps far more often than a person does. On a big repo, every slow grep costs time and tokens. Honest notes: patterns with no useful trigrams still scan everything, and the index can fall behind your edits. Big files and binary files are skipped by default, and the regex engine isn’t PCRE2. MIT. Best for: agents working in large repos.

  • XERJ — a local Rust search engine, with a Corpus Hub that makes it more interesting than another search tool. The engine indexes code, docs, logs, tables, and PDFs; code keeps its symbols and line references. It offers BM25, vector, and hybrid search through a CLI, MCP, and an Elasticsearch-compatible API. Its reference-coding workflow is simple: retrieve how an unfamiliar project solves a problem before writing your own implementation. A small project-run study reports 2.7× fewer output tokens than a grep-driven agent, with both solving 16/16 runs across eight tasks. The README says the gains depend on unfamiliar material; retrieval can add cost on libraries the model already knows. Apache 2.0.

    But XERJ Corpus Hub is the part I want to keep watching. In July I wrote about a hub of knowledge: people prepare domain packs once, publish them, and let agents bring them into their own stores. XERJ gives that idea a concrete home. Browse sources by domain, from database implementations to API specifications and operations runbooks. Its overview describes pinned sources, licence reviews, signed search packs, and local queries that return passages with file and line references. The work of choosing and preparing reference material becomes something the next agent can reuse. You can change the model and keep the reference library.

    There is an evaluation story too. The agent guide distinguishes retrieval spot checks from agent A/B results: can search find useful passages, and does the same agent do better with the corpus than without it? Many entries remain ungraded, and a handful of test queries cannot establish expertise across a domain. Still, publishing the evidence is the right move. The next step from my July sketch is composition: when public reference material meets your private project facts, derive the connections, settle conflicting versions, and keep the result with its sources. A searchable pack supplies evidence for that work. I want the useful conclusions to survive the session too. Best for: reusable reference libraries for agents, and a working example of how a knowledge hub could begin.

4. Below the token

  • Breaking the Token Ceiling — last month I picked tiktoken back up and called it the ruler. This paper asks if we need the ruler at all. It compares small models that read tokens with ones that read raw bytes, both learning from a bigger teacher model (distillation). The problem is that the teacher speaks tokens. So they give two ways to turn a token model’s predictions into byte predictions, one approximate and one exact. The finding is a crossover. Token models win early, then level off. Byte models start weaker, keep climbing, and pass them with more compute. Byte models also need less data: they match the distilled token model with about a sixth of it. And with only 256 possible bytes, the teacher’s outputs are much cheaper to store. Honest notes: the biggest wins are predicted from scaling laws, not measured, and the models are small. Best for: a hint at what comes after the transformer as we know it. Maybe it’s not a new architecture. Maybe it’s the end of the tokenizer.

5. Machines for agents

  • forkd — fork() for agent sandboxes. Boot one parent microVM, load the runtime (Python, packages, even a model), and pause it. Then spawn children that share the parent’s memory, copy-on-write, until they change something. Each child is a real Linux VM with hardware isolation, its own network, and a memory limit. It starts fast because nothing boots from cold. The feature that caught me is BRANCH. You pause a running sandbox mid-task, snapshot it, and fork from there. An agent at a fork in the road can try both paths for real. I wrote that you can’t fork yourself. Your agents increasingly can, all the way down to the machine. Honest notes, all from the README: it’s alpha and runs on one host only. Outgoing network traffic is not blocked by default, so bring your own firewall rules. Only memory is limited, there’s no security audit yet, and snapshots don’t move across CPU types. Apache 2.0. Best for: search, parallel tries, and RL rollouts where every branch needs a real machine.

  • Cua — computers that agents can use, in many pieces. There are full desktops for agents: local macOS VMs or Linux images, on your machine or your own cloud account. There’s a driver that operates native apps and browsers, often in the background, without stealing your mouse. There’s a VM manager for Apple Silicon, one SDK across several languages, and a benchmark that exports agent runs for training. Their idea of “computer-use 2.0” is an agent that moves between code, APIs, and the screen inside one task. It also ships CUA-S1: small models for fast, bounded computer-use decisions like filling in forms. That’s group 1 again, showing up at the screen. Honest notes: the licenses are mixed (mostly MIT, some parts source-available, a few AGPL pieces). Several old packages are deprecated, one has known security issues, and CUA-S1 is an early research release. Read the notices before you install. Best for: agents that must use real desktop apps, not just APIs.

  • llmfit — one command that looks at your CPU, RAM, GPU, and memory, and tells you which open models will actually run well on your machine. It scores each model on fit, estimated speed, quality, and context. It shows the inputs behind every estimate, so you can check it. You can benchmark your real speed, and your numbers replace the estimates. It has a terminal UI, a CLI, a web dashboard, a REST API, and JSON output for scripts and agents. MIT. Honest note: speeds are estimates from specs until you benchmark, and the community data is only as good as what people submit. Best for: starting at the cheap end. Before you rent a model, know what you can already run for free.

  • LLM Stats — a place to compare the models themselves: benchmark scores, API pricing, output speed, and context windows, with side-by-side comparisons and filters for open-weight models. It fits next to llmfit. One asks what your machine can run; the other helps you compare what those models offer against the ones you can rent. The useful part is seeing quality, speed, and cost together, because the highest-scoring model isn’t automatically the right one for every step of an agent. Honest note: a leaderboard is a shortlist, and public benchmarks don’t tell you how a model will perform on your own tasks. Best for: narrowing the models to test before committing to a provider or a local setup.

6. Teams and reach

  • OpenRig — a self-hosted setup for a long-lived team of coding agents (Claude Code, Codex, and Pi together) on projects that run for weeks. You talk to one lead agent. It proposes a team, you approve it, and it hands work to specialists, tracks it, and reports back. Agents can message each other for quick questions, or take tasks from an owned work queue, so you always know who has what. A terminal dashboard shows where they need you. The idea I liked: specialists keep what they learned. So work goes to whoever already knows that part of the project, like on a real team. It’s August’s fleet manager, but with long-lived colleagues instead of one-off runs. Honest notes: it’s early (not yet 1.0), and it needs tmux and signed-in agent CLIs. The site doesn’t state a license, so check the repo. The demos use staged output. Best for: one person running a small, long-lived agent team.

  • REA — Reverse Engineer Anything — one MCP server that lets an agent take software apart. It covers native binaries (through Ghidra, IDA, or Hopper), Electron and JavaScript apps, .NET, Android, websites, network and packet captures, firmware, WASM, smart-contract bytecode, and more. Analysis runs locally. Results come with evidence and a list of unknowns, not just a confident story. Setup registers it with the common coding agents. MIT, with clear rules: bring your own legal copies of commercial tools, and use it only on software you own or are allowed to examine. Honest notes: deep native analysis needs one of those heavy tools installed, and many targets need extra tools you supply. Best for: making software work together, security research, and understanding the black box you inherited.

The fast brain and the slow brain

Line the groups up and one idea runs through most of them: stop paying the slow brain for fast work.

The decision models in group 1 are the clearest case. But once you look, it’s everywhere. Jev-Mem keeps the reasoning model out of the memory’s way. Cua has a small model for bounded clicks. tgrep stops an agent from reading every file to find one line, while XERJ brings back the passage it needs from an unfamiliar codebase. Selective Forgetting shows you can drop a tenth of a memory and barely notice. Even the harness paper fits: instead of a bigger model, it improves the cheaper program around it. ECC’s observer is the same move: a small model reads the logs in the background while the big one works. Each one moves a routine judgment out of the expensive, open-ended model and into something smaller, faster, and bounded.

PageIndex is the honest exception. It spends more model thinking at search time, not less. But it fits the other half of the lesson: use the slow brain where judgment really matters, like deciding which section answers your question.

I keep saying the model is the rented part and the system around it is the job. This month added one more rule: not every part of the system should be the big model. Some of it should be a fast brain that says yes, no, this one. And it should know when to say I’m not sure, ask the slow one.

Here’s the question I’ll leave open: if the fast brain decides which calls reach the slow brain, who’s really running the agent?

Postscript: specs before code

One more crossed my desk after this was written, and it belongs next to the fast brain. Decision models make the small calls cheap. But an agent still needs to know what to build in the first place. That’s the job of a spec, and there are now two popular open tools for it.

  • OpenSpec (repo) — a light spec-driven development layer for coding agents. You and the agent agree on what to build, in writing, before any code. The flow is a few slash commands: explore the problem and the codebase, propose a change, apply it, optionally verify it against the spec, and archive it. The design choice I like is the split between two folders. changes/ holds work in progress: a proposal (why and what), the spec changes, a design, and a task list. specs/ holds the living source of truth. When a change is done and archived, its spec changes are merged into specs/. So the spec isn’t a document you write once and forget. It grows with the code, one change at a time. Requirements are plain Markdown, written as “SHALL” statements with WHEN/THEN scenarios. It works with many coding agents, and it’s built for existing codebases as well as new ones. There’s also a beta “stores” feature that keeps specs in a separate repo, so a platform team can own specs that product teams only read. MIT. Honest notes: it needs Node, it sends anonymous usage data by default (you can turn it off), and the adoption numbers on its site are its own. Best for: adding specs to a codebase you already have, one change at a time.

  • Spec Kit — GitHub’s toolkit, the one OpenSpec compares itself to. Same goal, heavier structure. You start with a constitution: a one-time file of project principles, like code quality and testing rules. Then a feature moves through clear phases: specify (what and why), plan (how), tasks, implement, and converge. You repeat implement and converge until the work matches the spec. Each phase is reviewed before the next. It has also grown past features. Extensions add a bug flow, which assesses, fixes, and tests, and only a verified verdict counts as fixed. An idea assessment flow ends in go, needs clarification, or kill. There are presets, workflows, private catalogs, and offline use for bigger teams. MIT. Honest notes: it needs Python and uv, its main examples are new projects (existing code has its own guides), and community extensions aren’t audited, so read them before you run them. Best for: teams that want firm phase gates and a shared process.

A fair warning about this table: the “light vs. heavy” framing comes from OpenSpec’s own README, so it’s one side’s view. Spec Kit’s extra steps are the point if your team needs them.

My pick: I’d start with OpenSpec for a codebase I already have. Its change-then-merge model matches how real work arrives: one change at a time, on code that already exists. I’d pick Spec Kit when a team needs the same process for everyone, with firm gates and a constitution everyone signs up to. Either way, the lesson is the same as the rest of this post. When code is cheap, the spec is the expensive part. It’s what tells the agent what “right” means, and it’s what you check the work against.
