Modern AI Agent System

Today most people meet AI agents in one shape: one person with one coding agent. A developer works with GitHub Copilot in the editor or in the terminal. Or each person on a team runs Claude Code, Codex, or OpenCode on their own machine. I think this is only the first step. A coding agent is one worker, and it still needs a person at the keyboard. The system I have in mind is larger. Call it a fleet: many agent teams in many sandboxes, run from one hub. It works for a whole organization, on every kind of work, not only code, and most of the time nobody watches it run. This post is my picture of that system. Each section stands on its own, so you can read them in any order.

Six building blocks and why each must exist

Each block below exists because something specific breaks when it is missing. That gives a simple test for any new tool in this space: which failure does it remove? If nobody can name the failure, the tool is not a building block yet.

  1. Memory system and memory hub. A model forgets everything when its session ends. Without memory, every run pays again to learn the same things: where things live, which tool is slow, which rule failed last time. Memory keeps what one run learned for the next one. The hub goes one step further and shares it across agents and sandboxes, so a lesson learned in one sandbox is read in all of them. XERJ is one example of the memory part: a search engine built for agents that also keeps a separate memory for each agent. Sharing across sandboxes is still the hub’s job. Memory is also where the agent system meets the context system, a point the section “One hub, many sandboxes” comes back to.

  2. Agent hub. An agent is more than a model. Around the model sit a profile, its standing rules, and its skills. Call that bundle a pack. Without a hub, every team is set up by hand, and the teams slowly drift apart. A hub stores packs the way a package registry stores libraries: versioned, installable, and the same in every sandbox. Claude Code Templates is a catalog of ready-made agents, commands, skills, and hooks, each installed with one command. ECC bundles skills, instincts, and memory into one pack that installs into several coding agents. Both serve coding agents today. The hub I have in mind serves every kind of agent.

  3. Orchestration system. Someone must decide which item goes to which sandbox. That is the orchestrator’s job. Someone must also start the team, stop it, and restart it when it crashes. Inside each sandbox, that job belongs to a supervisor. Without them, a crashed run just sits there, and nobody notices until the deadline. OpenRig shows the shape for coding agents. A lead agent hands work to specialist agents and tracks it. The team is built to keep running on projects that take weeks.

  4. LLM provider and routing system. The model is rented. Every provider has outages and a different price for each model, and its usage limit can stop a long run halfway. A routing layer sits between the agents and the providers. It sends each call to the right model, spreads the load, and switches when a provider fails. ccflare does part of this for Claude and OpenAI calls. It spreads requests across several accounts and moves to another account when one hits its limit.

  5. Monitoring system. When nobody watches the run, its logs and traces are the only witnesses. Without them, nobody can say why a run failed, what it cost, or which step wasted the most turns. The person who improves the system then has nothing to read. Langfuse traces agent runs so they can be evaluated and improved. OpenTelemetry is the open standard for collecting traces, metrics, and logs from any service.

  6. Sandbox and special runtime environment. An agent acts, and a normal machine is often the wrong place for it to act. First, its actions need a sandbox: a safe, throwaway place where they can be checked before they touch anything real. E2B gives every agent session its own small virtual machine for this. Second, some work only runs in a special environment that a normal machine cannot provide. Code for a mainframe needs a mainframe, or a faithful copy of one, to build, run, and test. The same holds for other platforms a normal machine cannot run. Without this block, the agent either acts on the real system or cannot do the work at all.

One hub, many sandboxes

A fleet grows by adding sandboxes, not people. For each piece of work, the hub does the same three things. It sets up a working environment in a sandbox. It clones an agent team into it from the agent hub. Then it connects the team to the knowledge base. The person stays in one place: the hub, where the logs come in and the packs go out.

The hub holds the team packs, assigns each item to a sandbox, and collects every sandbox’s logs. Inside the sandbox, a supervisor starts, stops, and restarts the team. The team is cloned, not built by hand. A lead and its specialists come from the same packs every time, so ten sandboxes run ten copies of the same team. Next to the team sits what the work needs to run: its tools, plus a mainframe or a copy of one where the work calls for it. Three things stay outside and are rented: the work queue, the system of record where finished work lands, and the model provider. Next to the system of record sits a checker, the part that says whether the work is right. For code it is the tests and CI. For back-office work it is business rules or reconciliation.

The fleet diagram spreads the same building blocks across many sandboxes. The hub and the supervisors are orchestration, and the hub is also the agent hub. The router is the routing system. The knowledge base is memory. The logs are monitoring. The sandboxes and their runtimes are the sixth block.

One box is marked as owned: the knowledge base and memory hub. It is the one part nobody can sell you, and every team both reads it and writes lessons back. This is where the context system lives, and where it meets the agent system. When Code Is Cheap splits today’s work into two kinds: building the agent system, and building the context system around it. Most of this post is about the first kind. The second kind decides what the agents are given. That post explains why it is hard, and how the hard part changes as an organization grows.

A fleet multiplies whatever context it is given, good or bad, so the context system matters more here. With one developer and one agent, a stale fact gives one wrong answer, and the developer usually catches it. With a fleet, the same stale fact is read by every team, on every item, until someone fixes it. So the knowledge base needs an owner, and a fact is fixed once, at the source, not in a hundred transcripts. The same holds for the lessons the teams write back. A wrong lesson spreads as fast as a right one, so the owner reviews a lesson before every team reads it as a rule.

The flow also runs the other way. The logs that reach the hub show which facts each agent used and where it went wrong. That makes the fleet the strictest test of the context system: every checked run is also a test of what the agents were given.

The life of one task

Every task runs through the same loop, whatever the work. Only the runtime and the checker change. A bug fix, an invoice that does not match, and a research question all pass through the same stages:

flowchart TB
  A["take an item<br/>from the queue"] --> B["set up the sandbox,<br/>clone the team"]
  B --> C["read the rules<br/>knowledge base, decisions, past lessons"]
  C --> D["plan<br/>write down what done looks like"]
  D --> E["do the work<br/>in the runtime"]
  E --> F{"does the<br/>checker pass?"}
  F -->|"no, time left"| E
  F -->|"yes"| G["hand back the result<br/>with its evidence"]
  F -->|"stuck or out of time"| H["hand back what is verified,<br/>name what failed"]
  G --> I["write the lesson,<br/>close the sandbox"]
  H --> I

Two stages matter most. The plan comes before the work and writes down what done looks like, so the checker has something to check against. The loop also has a way out. When the team is stuck or out of time, it hands back what it has verified and names what failed. That beats an answer that only looks finished. At the end, writing the lesson makes the next task of the same kind cheaper, and closing the sandbox makes sure it starts clean.

How to distribute work across agents

A second agent saves real time only when the queue backs up, that is, when the first agent is busy most of the time. If items arrive well apart, each one is done soon after it arrives. The finish time is then set by when the last item arrives, not by how many agents work, and a second agent buys almost no time. This is old queueing arithmetic. In 1917, A. K. Erlang published formulas for lost and delayed calls. Engineers used them to work out how many lines a telephone exchange needs for a given flow of calls. Extra lines pay off when the ones you have are busy most of the time. When they are mostly idle, nobody is waiting, so the new ones sit idle too.

So the work is sequential by default. Spawn a worker only when the open work will not fit before a deadline. This holds for any queue, not only code: support tickets, invoices to match, test runs on phones. A fleet grows by the same rule: it adds a sandbox when a queue backs up, not before.

When you do spawn, five rules keep the workers out of each other’s way:

When you do spawnRule
Isolationits own workspace: a worktree, port, build cache, and database for code; its own device or test account for other work
Briefonce and complete: the item, the workspace, the deadline, the names of the evidence to return
Reportonly when done or blocked
Ownershipone agent writes the final result (a commit and push, a ticket update, a filed form) and hands back
Rolesnamed profiles whose standing rules travel with them, not a generic worker

The five rules share one idea: workers never talk to each other. Each one gets a brief and hands back a result, and anything else it learns goes to the memory hub.

Do we still need a human in the loop?

A person is needed to check the work only where the target is vague. Say the agent can check the result itself: steps a, b, c, and d are done, or the math problem is solved. Then why do we need a human in the loop? So autonomy has one condition: the target must be clear and checkable. A checkable target also makes autonomy measurable, with two numbers: the cost, in tokens, and the number of results that passed the check.

Many companies aim for autonomy with goals like “increase sales 100%”. That is a moving target. It cannot be checked in time, and the result cannot be traced back to the agent. The fix is to break the goal into targets the agent can check: reply to every lead within five minutes, follow up every deal that has gone quiet. The human owns the goal; the agent owns the targets.

The unattended version takes this all the way: zero people during the run. The person’s seat moves to between runs. We read the transcripts and edit the pack (the agent’s profile, rules, and skills). We change only a few things per run, so each effect can be traced to its cause. Then we run again. An earlier post, on migration as a harness, quotes the rule behind this: “you don’t fix the code — you fix the process that produced the code.”

A clear target takes the person out of checking, not out of approving. What the agent may do alone is a separate question, about authority, and it is decided per action. When Code Is Cheap gives the rule: reading can be logged, writing needs a person to confirm, and anything destructive needs separate approval. In a fleet, a person can hand the confirming seat to the checker for writes it can test. The push lands only if CI passes, and the form is filed only if the business rules pass. When Code Is Cheap says the same for migration: commit only what the judge passed. Every other write waits for a person between runs.

Lesson: make the result of your work precise and checkable before you ask for autonomy.

Why one harness doesn’t fit all

A harness is only as good as the checker you can build for its domain. By harness I mean everything around the model: tools, state, the loop, the checks, the limits. Each kind of work needs its own, because each kind of work is checked in a different way.

Coding harnesses matured first because code has the strongest built-in checker: the compiler and the tests say right away whether it worked. The other harnesses are behind not because the models are worse, but because their work is harder to check. So designing a new harness starts with one question: how does this agent know it’s done, and done right?
